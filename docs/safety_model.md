# RIFT — Safety Model
**Phase 2 | Version 1.0**

---

## Part O — Safety Model for Runtime Interventions

### O.1 Core Safety Principle

> **RIFT must never execute interventions on systems handling real user traffic or storing irreversible production data without explicit operator authorization and safety-layer approval.**

RIFT is designed for:
1. **Isolated research testbeds** (Docker Compose / Kubernetes clusters running benchmark applications)
2. **Shadow/staging environments** that mirror production topology but serve no real users
3. **Production systems** only under an explicit elevated authorization protocol with automated rollback, blast-radius budget, and kill-switch supervision

For the ICSE evaluation, RIFT operates exclusively in isolated testbed environments.

---

### O.2 Sandboxing

**Testbed sandbox requirements:**

| Property | Requirement |
|---|---|
| Network isolation | All services run in a dedicated Docker network / K8s namespace with no egress to production |
| Data isolation | All databases are seeded from anonymized snapshots; no production data |
| Traffic isolation | Synthetic load generated by a local workload generator; no real user requests |
| Metrics isolation | Prometheus/Jaeger collect only from sandboxed services |
| Intervention isolation | tc netem / cgroup modifications apply only to target container's network namespace |

**Namespace enforcement:**
- Every intervention mechanism must verify the target container is within the designated RIFT sandbox namespace before executing
- Out-of-namespace targets are rejected with SANDBOX_VIOLATION error

---

### O.3 Rollback

Every intervention has an associated rollback procedure, defined at planning time:

| Intervention Type | Rollback Mechanism | Rollback Time |
|---|---|---|
| Latency injection (tc netem) | `tc qdisc del dev eth0 root` | < 1s |
| Error injection (sidecar) | Disable sidecar; restore original handler | < 5s |
| CPU throttling (cgroup) | Remove cpu.cfs_quota_us limit | < 1s |
| Memory limit (cgroup) | Remove memory.limit_in_bytes | < 1s |
| Network partition (iptables) | Flush iptables rules | < 1s |

**Automatic rollback triggers:**
- Intervention recovery check fails (X does not return to baseline within Δ_recovery = 120s)
- Kill switch activated (see O.7)
- Safety module detects unintended side effects (side_effects ≠ [])
- Timeout: intervention exceeds Δ_int_max without producing sufficient observations

All rollback operations are idempotent and logged.

---

### O.4 Intervention Authorization

**Authorization levels:**

| Level | Who authorizes | Interventions allowed |
|---|---|---|
| AUTO | RIFT safety module (automatic) | BR < 0.10, SLAI < 0.02, RC = 0, SC ≤ MEDIUM |
| SUPERVISED | Operator acknowledgement required | BR < 0.30, SLAI < 0.05, RC = 0, SC ≤ HIGH |
| ELEVATED | Named operator + written justification | Any SC, RC ≤ MEDIUM |
| BLOCKED | Cannot execute | RC = HIGH (data-state modifications), production environment |

Default for ICSE evaluation: AUTO authorization for all qualifying testbed interventions.

---

### O.5 Blast-Radius Constraints

**Blast radius** BR(I) = fraction of services expected to be observably affected:

```
BR(I) = |Desc(X, G_T) ∩ S| / |S|
```

Hard limits by authorization level:

```
AUTO:       BR(I) < 0.10
SUPERVISED: BR(I) < 0.30
ELEVATED:   BR(I) < 0.60
```

If BR(I) ≥ 0.60, the intervention is blocked regardless of authorization level — the risk of cascading the incident is too high.

**Blast-radius pre-flight check:** Computed analytically from G_T before any intervention is dispatched.

---

### O.6 Data Isolation

RIFT never executes interventions that:
- Modify database row data (INSERT/UPDATE/DELETE)
- Consume external API quota or credits
- Send emails, notifications, or messages to real users
- Write to persistent storage outside the sandbox namespace

Data-modifying interventions are classified RC = HIGH and are **BLOCKED** for automatic execution.

---

### O.7 Kill Switch

RIFT maintains a **global kill switch** — a single-operation stop command that:

1. Immediately removes all active intervention mechanisms (parallel rollback)
2. Stops the attribution loop
3. Writes ABORTED status to all pending InterventionRecords
4. Produces a kill-switch incident report

Kill switch is triggered by:
- Operator manual invocation (CLI: `rift kill`)
- Watchdog detecting SLO violation > 2× the SLAI budget
- Watchdog detecting RIFT's own resource usage > 10% of target system resources
- Any rollback failure (intervention cannot be removed within Δ_recovery = 120s)

Kill switch response time: < 5 seconds for all active interventions.

---

### O.8 Failed Intervention Handling

When an intervention fails (mechanism cannot be applied, or cannot be removed):

```
Step 1: Attempt rollback immediately
Step 2: If rollback fails within 30s: activate kill switch
Step 3: Log INTERVENTION_FAILED event with full system state snapshot
Step 4: Notify operator (alert via configured channel)
Step 5: Mark all attribution results from this incident UNRELIABLE
Step 6: Require human review before RIFT resumes on this system
```

RIFT does not silently continue after a failed rollback. Any unresolved intervention leaves the system in an undefined state, invalidating causal assumptions.

---

### O.9 Safety Summary

| Property | Mechanism | Guarantees |
|---|---|---|
| Sandboxing | Namespace isolation | No production impact in testbed mode |
| Rollback | Per-intervention rollback procedure | System returns to baseline within 120s |
| Authorization | 4-level auth protocol | No high-risk interventions without approval |
| Blast radius | Pre-flight BR check | ≤ 30% of services affected (supervised) |
| Data isolation | Blocked RC=HIGH class | No irreversible data modifications |
| Kill switch | Global stop command | All interventions removed within 5s |
| Failed intervention | Automatic rollback + kill switch | No silent failures |
