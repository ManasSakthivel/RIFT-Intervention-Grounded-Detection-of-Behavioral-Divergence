# RIFT Dataset Provenance (Sprint 4.2.4, Issue 4)

**Purpose.** Reconcile the "69 scenarios" figure in the historical manifest with the "50-scenario development set" and the actual files. Record, for every dataset, where it came from and whether it was used to choose thresholds.

**Status of this document.** The facts below come from three sources:
- re-running `SyntheticBenchmark().generate_all_faults(42)`;
- hashing the files in `datasets/rift_faults/`;
- diffing the two.

They are reproducible with `python3 scripts/sprint424_build_dataset_manifest.py --check` and `python3 -m pytest -q -p no:cacheprovider tests/unit/test_sprint424_dataset_manifest.py`. Nothing in this document changes a historical record. The original manifest is preserved byte-for-byte as `datasets/rift_faults/manifest.v1_generator_69.json`.

## 2. Why 69 and 50 differed

1. `manifest.json` reported `total_scenarios = 69` with split counts 36 / 18 / 15. Re-running the generator at seed 42 yields exactly 69 scenarios with those split counts (48 confounded). The historical manifest is therefore a correct description of the **generator output**.
2. `development.json` holds **50** scenarios, not 36. The 36 generator scenarios are present and field-identical. The other **14** were added by hand during the P0-02 remediation (`docs/FINAL_PRE_LINUX_COMPLETION_REPORT.md`): 11 `MULTI_CAUSE` (`MC_02`–`MC_12`) and 3 `AMBIGUOUS_ATTRIBUTION` (`AA_01`–`AA_03`). The aim was to give the H3 multi-cause filter n = 15.
3. The manifest was never regenerated after that expansion. "69" (generator) and "83 = 50 + 18 + 15" (deployed) therefore coexisted. Documents quoting "50 development scenarios" and documents quoting "69 scenarios" were each consistent with a different object.
4. The expansion added no `CONFOUNDED` scenarios. The confounded count (48) and the H2 power note are unchanged.

Reconciliation: `83 (deployed) − 69 (generator) = 14 (hand-added, all in development)`.

### What changed in Sprint 4.2.4

- `manifest.json` is now schema `rift.dataset_manifest/2`.
  - It keeps the legacy keys (`seed`, `total_scenarios`, `non_confounded`, `confounded`, `by_fault_type`, `split_counts`, `h2_power_note`) with the **deployed** values: 83 total; DEV 50 / VAL 18 / HELD 15.
  - It adds `generator_output`, `files`, `reconciliation`, `fault_id_collisions_across_files`, and `held_out_scenarios_with_content_twin_in_other_split`.
- `src/rift/fault_injection/fault_injector.py` checks the manifest at import time. Its expected development count changed from 36 to 50 (`MANIFEST_SPLIT_DEVELOPMENT`) so that it matches the deployed corpus. It still rejects the historical generator manifest. The test is `test_fault_injector_rejects_the_stale_generator_manifest`.
- No scenario file was modified.
- The dataset-version hash recorded by `src/rift/provenance/logger.py` (SHA of `manifest.json`) changes as a consequence. This is expected.

## 3. Content duplication across splits (disclosure)

Scenarios are generated from templates. Ignoring `fault_id`, `name`, `seed` and `split`, the 83 deployed scenarios contain only **25** distinct contents.

| Template family | Copies | Splits containing the content |
|---|---:|---|
| `NL`, `PL`, `SD`, `RC` (one content each) | 3 each | development, validation |
| `QU` | 3 | development, held-out |
| `DF`, and the `MC_01/02/03` template | 3 each | development, validation, held-out |
| `CF` (4 distinct contents) | 12 each | development, validation, held-out |
| hand-added `MC_02`–`MC_12` and `AA_01`–`AA_03` (as stored in development) | 1 each (14 distinct) | development only |

**Every one of the 15 held-out scenarios has a content-identical twin in development or validation.** The 15 are `CF_36`–`CF_47`, `QU_03`, `DF_03` and `MC_03`. They differ from their twins only in id, name and seed.

The held-out split is separated by file, seed and label. It is **not** content-independent of the development and validation data. Results on it measure generalisation to new random seeds of known templates, not to new fault structures. Any claim that depends on held-out independence must carry this qualification.

This is a pre-existing property of the generator. Sprint 4.2.4 did not change it and does not claim to fix it.

## 4. Fault-id collisions across files

Two `fault_id` values appear in two different files with **different** content (root cause, seed, path):

| fault_id | File A | File B |
|---|---|---|
| `MC_02` | development (root `redis_cart`, seed 100; hand-added) | validation (root `payment`, seed 44; generator) |
| `MC_03` | development (root `product_catalog`, seed 101; hand-added) | held-out (root `payment`, seed 45; generator) |

Hence 83 scenarios but 81 unique ids. Within each file, ids are unique. Any analysis that joins results from several splits by bare `fault_id` will merge unrelated scenarios, so join on `(split, fault_id)`. The hand-added ids were not renamed. Renaming would alter pinned data files and invalidate historical results.

## 5. What was used for selection, and what was not

- **Sprint 4.2.3 detector thresholds** were selected on:
  - development (50);
  - validation (18);
  - adversarial per-family indices 01–03 (18);
  - 300 synthetic stress series (seeds 0–299).
- **The final stage** read the held-out file, adversarial indices 04–05 and stress seeds 1000–1299. It did so only after `thresholds_frozen.json` was hashed.
- **Held-out has been read before.** `docs/FINAL_HELD_OUT_EVALUATION.md` records an earlier final evaluation of the comparative methods on it. Sprint 4.2.3 read it once more for the frozen detector comparison. Neither used it to choose a parameter in Sprint 4.2.3. It is still not a pristine, never-seen set, and the content-twin issue in §3 further limits its independence.
- **As of Sprint 4.2.4** the loaders (`src/rift/evaluation/dataset_registry.py`) refuse to return held-out labels unless two conditions hold:
  - the call states `purpose="final"`;
  - it presents a `HeldOutGuard` with an active oracle token.
  
  Calls for threshold selection are rejected regardless of the guard.
